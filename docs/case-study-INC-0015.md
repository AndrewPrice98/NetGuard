# Case study: adversary-in-the-middle on a home network

> **Lab exercise.** This is a purple-team exercise against a fictional network,
> not a real compromise. The attack traffic is the committed capture
> [`samples/mitm_kill_chain.pcap`](../samples/mitm_kill_chain.pcap), generated by
> `netguard simulate`. Every timestamp and frame number below can be checked by
> opening that file in Wireshark or running
> `netguard pcap samples/mitm_kill_chain.pcap`.
> The dashboard's demo (`netguard demo`) shows the same incident as **INC-0015**.

## 1. Summary

| | |
|---|---|
| **Incident** | INC-0015, Adversary-in-the-middle attack chain |
| **Severity** | Critical |
| **Classification** | True positive, active interception attempt |
| **Attacker** | `de:ad:be:ef:13:37` / `192.168.1.87` (hostname `kali`, randomized MAC) |
| **Victim** | `a4:83:e7:2b:11:5c` / `192.168.1.20` (Alex's MacBook) |
| **Impersonated** | Default gateway `192.168.1.1` (real MAC `f0:9f:c2:10:20:01`) |
| **Attack window** | 2026-01-15 14:01:00 to 14:03:28 UTC (capture end) |
| **ATT&CK** | T1200 → T1046 → T1557.002 |

An unknown device leased an address from the router, swept the NAS and a
laptop for open services, and about 90 seconds later began sending forged ARP
replies telling the laptop that the router's IP address belonged to the
attacker's MAC. If the laptop accepted them, all of its off-network traffic
would pass through the attacker.

NetGuard raised a HIGH `port_scan` alert at the first sweep and a CRITICAL
`gateway_arp_spoof` alert **on the first forged packet** (frame 148). The
correlation engine grouped them, together with the scan-time `new_host` and
`new_port` alerts in the demo, into one incident spanning four ATT&CK
tactics.

## 2. Detection

| Time (UTC) | Frame | Alert | Severity |
|---|---|---|---|
| 14:01:30 | 56 | `port_scan`: 192.168.1.87 probed 15 ports in 10 s | HIGH |
| 14:03:00 | 148 | `gateway_arp_spoof`: gateway 192.168.1.1 claimed by de:ad:be:ef:13:37 | CRITICAL |

The scan alert fired on the 15th distinct port, 0.3 s into the sweep. The
spoofing alert fired on the first forged reply; the 14 replies after it were
held back by the rule's 5-minute cooldown, so one condition produced one
alert.

## 3. Timeline

Reconstructed from the capture. Times are UTC on 2026-01-15.

| Time | Frame(s) | Event |
|---|---|---|
| 14:00:00 | 1–23 | Baseline traffic. Laptop gets a DHCP lease from the router (frame 2: offer, router and DNS = 192.168.1.1), resolves the gateway and the NAS, opens HTTPS and SMB sessions. NetGuard learns 192.168.1.1 as the trusted DHCP server and gateway. |
| 14:01:00 | 24–25 | **Initial access.** New MAC `de:ad:be:ef:13:37` broadcasts a DHCPDISCOVER; the router offers `192.168.1.87`. The attacker is now on the network with a legitimate lease. |
| 14:01:01 | 26 | Attacker announces itself via ARP (`192.168.1.87 is-at de:ad:be:ef:13:37`) and resolves the gateway. |
| 14:01:30 | 28–86 | **Discovery.** SYN sweep of the NAS (`192.168.1.10`): 30 SYNs to 29 distinct well-known ports (21–27017) in 0.6 s. The NAS answers SYN-ACK on 22, 80, 443, 445 and 5000, revealing its services. |
| 14:01:35 | 88–146 | Second sweep, of the laptop (`192.168.1.20`): same 30 probes. |
| 14:03:00 | 148 | **Credential access / collection.** First forged ARP reply to the laptop: `192.168.1.1 is-at de:ad:be:ef:13:37`. |
| 14:03:00–14:03:28 | 148–162 | 15 forged replies at 2 s intervals, the refresh pattern of `arpspoof` keeping the victim's cache poisoned. Capture ends. |

## 4. Analysis

**Why this is malicious and not misconfiguration.**

- The attacker's MAC is not in the baseline, uses a locally administered
  (randomized) address, and the device calls itself `kali`.
- The ARP replies are **unsolicited**. The laptop asked for the gateway exactly
  once (frame 3, 14:00:01) and the real router answered (frame 4). The 15
  replies from 14:03 onward answer no request at all, and are sent
  unicast to the laptop on a fixed 2-second timer.
- Two MACs claim `192.168.1.1` in the same capture. `netguard pcap` flags this
  directly in its host table:
  `de:ad:be:ef:13:37 … 192.168.1.1, 192.168.1.87 <- CLAIMS 192.168.1.1 (also f0:9f:c2:10:20:01)`.
- The order (join, enumerate services, then intercept) is a coherent attack
  chain, not the random noise of a misbehaving device.

**Something the alerts alone didn't show.** Only one `port_scan` alert fired,
but the capture contains *two* sweeps (NAS at 14:01:30 and laptop at 14:01:35).
The rule's 60-second per-source cooldown folded the second sweep into the
first alert. Nothing was missed for response purposes, since the source was
already flagged, but the laptop's exposure would have been under-reported
without going back to the packets. This is recorded as a known behaviour in
[DETECTIONS.md](DETECTIONS.md#port_scan), and is the reason incident reports
point to frame numbers.

**Scope.** No frame shows the laptop sending traffic to the attacker's MAC
after 14:03:00, so the capture does not prove the poisoning succeeded, only
that it was attempted continuously. In a real case the next step would be to
check the laptop's ARP cache (`arp -a`) and the router's client list, and to
assume interception for the purpose of credential rotation.

## 5. Indicators

| Type | Value | Note |
|---|---|---|
| MAC | `de:ad:be:ef:13:37` | Attacker. Locally administered (randomized). |
| IPv4 | `192.168.1.87` | Attacker's DHCP lease |
| Hostname | `kali` | From DHCP / reverse DNS. Attacker-controlled, low confidence. |
| Port | `tcp/4444` | Listener opened on the attacker (demo `new_port` alert); Metasploit's default handler port |
| Impersonated | `192.168.1.1` | Victim address being spoofed. **Not** an attacker IOC; do not block. |

## 6. ATT&CK mapping

| Tactic | Technique | Evidence |
|---|---|---|
| Initial Access | [T1200](https://attack.mitre.org/techniques/T1200/) Hardware Additions | Unknown device joins with a valid lease (frames 24–25) |
| Discovery | [T1046](https://attack.mitre.org/techniques/T1046/) Network Service Discovery | SYN sweeps (frames 28–146) |
| Persistence | [T1021](https://attack.mitre.org/techniques/T1021/) Remote Services | tcp/4444 listener (scan-time alert) |
| Credential Access, Collection | [T1557.002](https://attack.mitre.org/techniques/T1557/002/) ARP Cache Poisoning | Forged ARP replies (frames 148–162) |

## 7. Response

| Phase | Action |
|---|---|
| Containment | Block `de:ad:be:ef:13:37` on the router; disconnect it from Wi-Fi. |
| Containment | On the laptop: `arp -d *` (Windows) or `sudo arp -d -a` (macOS), then confirm 192.168.1.1 resolves to `f0:9f:c2:10:20:01`. |
| Eradication | Rotate the Wi-Fi passphrase: the attacker obtained a lease, so it has the passphrase. Review the router's client list for other unknown devices. |
| Recovery | Rotate credentials the laptop used over unencrypted or certificate-warned connections during the window. |
| Hardening | Static ARP entry for the gateway on critical hosts; client isolation on the Wi-Fi; a separate SSID for guests and IoT. |

## 8. Lessons learned and detection improvements

1. **Live capture closed the gap.** The scan-time rules (`gateway_mac_changed`,
   `arp_spoof`) would only have noticed the poisoning at the next 5-minute sweep,
   and only if the sensor itself was poisoned. The live ARP watcher alerted on
   the first packet.
2. **Correlation turned four alerts into one decision.** Seen one at a time,
   `new_host` (MEDIUM) and `port_scan` (HIGH) are routine. Grouped by device and
   ordered by tactic, they read as an attack chain before the critical alert
   even arrived.
3. **Improvement (backlog):** report scan *targets* in the `port_scan` alert, and
   re-alert when a flagged source sweeps a new target during the cooldown, so
   the second sweep in this capture would not be folded silently.
4. **Regression protection:** this capture is a permanent scenario
   (`mitm_kill_chain`) in `netguard validate` and in CI, so any change that stops
   either alert firing fails the build.
